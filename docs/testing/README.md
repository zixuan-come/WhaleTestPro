## 使用与执行准备

1. 先按模块和建议优先级筛选，核对来源和本场景前置，再在隔离测试环境执行。
2. `T` 为本轮团队，`P` 为目标项目，`Q` 为另一团队的项目；`I/J` 为接口，`C/C1/C2` 为用例，`E` 为环境，`S` 为场景，`U` 为套件，`D` 为调度，`F` 为压测任务，`M` 为 Mock。`R/SR` 等报告或录制符号按当前用例上下文解释。所有资源符号必须替换成准备步骤得到的真实整数 ID。
3. `ownerToken/adminToken/memberToken/outsiderToken` 必须替换为本轮角色的真实 Token。member 只加入 T，不加入 Q 所属团队；owner 可同时持有两个团队用于准备隔离数据。用例要求无成员的新账号、专用注销账号或空项目时，以该场景专用前置为准，并相应替换 Token 和项目 ID。
4. “本轮唯一名”“桩的真实地址”等是数据说明，不是可直接发送的字面值；中文路径需要 URL 编码。一般预置资源仅用于准备，专用前置要求“无引用/空集合/不同状态”时须调整或另建目标，不保留与专用前置冲突的资源。
5. 请求配置按 `headers/query/body` 分层。用例链和回归的 Body 是整数数组，不是 `{case_ids: [...]}`；流量回放的 `env_id/field_rules` 位于 JSON Body，不是查询参数。请求地址以接口路径为准，存在 `path_override` 时按其说明替换目标路径或 ID。
6. 下游请求使用可控 HTTP 桩，并验证请求次数与响应；SQL 测试只使用独立、受限的测试库。调度默认关闭；压测、并发、故障注入场景须单独安排隔离部署，不对生产系统、共享队列或他人数据执行。
7. 每条用例独立准备和恢复数据，不把主表行顺序当作执行依赖。故障、角色或权限变化必须恢复；仅逆依赖清理本轮资产。没有用户/订单清理接口的场景使用可重置的隔离库，不直接清空已有数据。
8. 执行后记录实际结果、环境、版本、时间及证据；不通过的场景关联真实缺陷。确认结果后再填写执行状态并形成测试报告。

后续路由或规则变化时，应同步更新 JSON、覆盖清单和 Excel；保留用例编号的可追踪性，重新核对来源与数量，不能沿用本轮设计齐全或执行结论。
