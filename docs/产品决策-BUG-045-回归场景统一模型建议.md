# BUG-045 回归/场景统一测试套件模型产品决策建议

## 决策问题
回归与场景两条路割裂，不符合 Apifox「场景即运行单元」心智，需要统一测试套件模型。

## 当前问题分析

### 现状架构
1. **回归（Regression）**：
   - 运行单元：散装用例（按 tag 或 case_ids 筛选）
   - 执行方式：`run_case`（逐条独立执行）
   - 报告：写入普通测试报告（test_reports）
   - 前端入口：Regression 页面
   - 定时调度：支持（通过 schedule 表，存 `cron + tag`）

2. **场景（Scenario）**：
   - 运行单元：编排的场景（case_ids 有序列表）
   - 执行方式：`run_chain`（链式传参）
   - 报告：写入场景报告（scenario_reports）
   - 前端入口：Orchestration 页面
   - 定时调度：**不支持**

### 核心问题
- ❌ 场景不能作为回归的运行范围
- ❌ 回归不能执行场景
- ❌ 定时任务只能跑散用例，不能跑场景
- ❌ 两套报告系统，数据割裂
- ❌ 不符合业界最佳实践（Apifox、Postman）

---

## 业界对标分析

### Apifox 模型
```
测试场景（Test Scenario）
  └─ 是编排单元（定义步骤和依赖）
  └─ 是执行单元（直接运行场景）
  └─ 是自动化单元（定时任务运行场景）
  └─ tag 只是筛选辅助
```

### Postman 模型
```
Collection（集合）
  └─ 包含多个 Request 或 Folder
  └─ 支持运行整个 Collection
  └─ Newman CLI 支持 Collection 自动化
  └─ 支持 Pre-request Script 和 Tests
```

### JMeter 模型
```
Test Plan（测试计划）
  └─ Thread Group（线程组）
      └─ HTTP Request（请求）
      └─ Assertions（断言）
```

## 推荐方案：统一为「测试套件」模型

### 方案概述
引入「测试套件（Test Suite）」作为顶层概念，统一回归和场景：

```
测试套件（Test Suite）
  ├─ 类型 1：场景套件（Scenario Suite）
  │   └─ 包含多个场景，场景内部链式传参
  ├─ 类型 2：用例套件（Case Suite）
  │   └─ 包含多个独立用例，按 tag 或手选
  └─ 类型 3：混合套件（Mixed Suite）
      └─ 既有场景，也有独立用例
```

### 核心改动

#### 1. 数据模型演进

**新增表：test_suites**
```python
class TestSuite(Base):
    id = Column(Integer, primary_key=True)
    name = Column(String(100))  # 套件名称
    description = Column(String(500))
    project_id = Column(Integer, ForeignKey("projects.id"))
    type = Column(String(20))  # "scenario" / "case" / "mixed"

    # 配置
    scenario_ids = Column(JSON)  # [1, 2, 3]
    case_ids = Column(JSON)      # [10, 11, 12]
    tags = Column(JSON)          # ["smoke", "p0"]

    created_at = Column(DateTime)
    updated_at = Column(DateTime)
```

**调整表：schedules**
```python
class Schedule(Base):
    # 现有字段保持
    # 新增字段
    suite_id = Column(Integer, ForeignKey("test_suites.id"), nullable=True)
    # 兼容：tag 字段保留，suite_id 为空时按旧逻辑
```

**统一报告：test_reports**
```python
class TestReport(Base):
    # 现有字段保持
    # 新增字段
    suite_id = Column(Integer, ForeignKey("test_suites.id"), nullable=True)
    suite_name = Column(String(100))
    execution_type = Column(String(20))  # "suite" / "scenario" / "case" / "regression"
```

#### 2. 执行引擎改造

**新增服务：suite_service.py**
```python
def run_suite(db, suite_id, project_id, env_id=None):
    """运行测试套件"""
    suite = suite_repo.db_get(db, suite_id, project_id)

    results = []

    # 运行场景（链式传参）
    for scenario_id in suite.scenario_ids:
        result = execution.run_scenario(db, scenario_id, env_id, project_id)
        results.append(result)

    # 运行独立用例
    for case_id in suite.case_ids:
        result = execution.run_case(db, case_id, env_id, project_id)
        results.append(result)

    # 按 tag 筛选用例
    if suite.tags:
        cases = case_repo.db_list_by_tags(db, project_id, suite.tags)
        for case in cases:
            if case.id not in suite.case_ids:  # 避免重复
                result = execution.run_case(db, case.id, env_id, project_id)
                results.append(result)

    # 写入统一报告
    summary = _calculate_summary(results)
    report = report_repo.db_create(
        db,
        suite_id=suite.id,
        suite_name=suite.name,
        execution_type="suite",
        results=results,
        summary=summary,
        project_id=project_id
    )

    return report
```

#### 3. 前端改造

**新增页面：TestSuites.vue**
- 套件列表（创建、编辑、删除、运行）
- 套件编辑器（拖拽场景、用例，配置 tag）
- 运行历史和报告查看

**调整页面：**
- **Regression.vue** → 改为「快速回归」或废弃，引导用户创建套件
- **Schedules.vue** → 改为选择套件而非 tag
- **Reports.vue** → 统一展示所有类型的报告

## 演进路径（分阶段实施）

### 阶段 1：最小改动（推荐优先做）
**目标：让定时任务支持运行场景**

改动：
1. `schedules` 表新增 `scenario_id` 字段（可选）
2. `scheduler.py` 支持：
   - 如果 `scenario_id` 有值，调用 `run_scenario`
   - 否则按原逻辑调用 `run_regression`
3. 前端 Schedules.vue 新增「运行类型」选择：
   - 按 tag 运行用例（旧）
   - 运行指定场景（新）

**优点：**
- ✅ 改动最小，风险低
- ✅ 立即解决"定时任务不能跑场景"的痛点
- ✅ 向后兼容

**缺点：**
- ❌ 仍然是两条路，没有统一

---

### 阶段 2：引入测试套件（中期演进）
**目标：统一运行单元**

改动：
1. 新增 `test_suites` 表和 CRUD 接口
2. 新增 `run_suite` 执行引擎
3. `schedules` 表新增 `suite_id`，关联套件
4. 前端新增 TestSuites.vue 页面
5. 报告统一标记 `suite_id`

**优点：**
- ✅ 彻底统一模型
- ✅ 更灵活：场景 + 用例混合运行
- ✅ 符合业界最佳实践

**缺点：**
- ❌ 改动较大，需要充分测试
- ❌ 用户需要学习新概念

---

### 阶段 3：报告系统重构（远期优化）
**目标：统一报告视图**

改动：
1. 合并 `test_reports` 和 `scenario_reports`
2. 报告详情页统一展示：
   - 套件信息
   - 场景列表（可折叠查看步骤）
   - 独立用例列表
   - 覆盖率、通过率统计
3. 支持对比两次运行结果
