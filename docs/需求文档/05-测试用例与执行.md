## 2. 背景与目标
测试用例把接口定义转为可重复、可判定的测试资产；执行器负责变量、SQL、请求、断言、提取、数据驱动和重试。

## 3. 范围
本期包含用例 CRUD、标签/优先级、断言、提取、setup/teardown SQL、数据集、重试、单条执行和链路执行；链路不继承数据集、SQL、重试。非本期范围为条件分支、循环、并发节点。

## 4. 角色与权限
项目成员可维护和执行当前项目用例；关联接口必须属于同一项目。

## 6. 功能需求
### CASE-F01 选择接口并创建、维护测试用例

**用户故事**

作为测试人员，我希望从当前项目已有的接口中选择测试目标，让系统复用接口的请求方法、URL、Header、Query 和 Body，而不是每次创建用例时重复填写请求信息。

**前置条件**

- 当前用户是项目成员。
- 当前项目至少存在一个可用接口。
- 被选择的 interface_id 存在且属于当前项目。

**主流程**

1. 用户进入新建用例页面。
2. 系统加载当前项目的接口列表。
3. 接口选项至少展示接口名称和请求方法，宜同时展示 URL，便于区分同名或相似接口。
4. 用户选择一个接口。
5. 系统通过 interface_id 建立用例与接口的关联，不复制保存接口请求模板。
6. 用户填写基础配置：用例名称、期望状态码、标签和重试次数。
7. 用户确有需要时展开“高级配置”，再填写断言、变量提取、setup/teardown SQL 和数据集。
8. 用户提交后，系统校验接口归属并保存用例。
9. 执行用例时，系统根据 interface_id 读取该接口最新的请求模板。

**业务规则**

- 用例必须选择一个接口，未选择时不能提交。
- 接口选择范围仅限当前项目，不能手工关联其他项目的接口 ID。
- 用例不重复保存 method、url、headers、params 和 body，避免接口定义与用例配置出现两份数据。
- 新建用例时高级配置默认折叠；编辑已有高级配置的用例时自动展开，并显示已配置项数量。
- 接口定义更新后，关联用例下一次执行使用最新接口配置。
- 编辑用例时可以更换关联接口，更换后仍需校验项目归属。
- 用例列表和详情应展示接口名称，宜同时展示请求方法，不能只向用户显示数据库 ID。
- 当前项目没有接口时，页面应展示空状态和“先创建接口”的引导，并禁止提交用例。
- 接口被删除后，用例记录暂时保留；执行时返回“用例关联的接口不存在”，不得发起 HTTP 请求。

**验收标准**

- Given 当前项目存在接口，When 用户新建用例，Then 可以从下拉列表选择接口，无需重新输入 method、url、headers、params 和 body。
- Given 用户未选择接口，When 提交用例，Then 前端提示“请选择关联接口”，请求不得提交。
- Given 当前项目没有接口，When 打开新建用例，Then 页面展示创建接口引导且不能提交。
- Given 用户选择当前项目接口并填写合法用例配置，When 提交，Then 创建成功并保存正确的 interface_id。
- Given 提交的 interface_id 属于其他项目或不存在，When 后端校验，Then 返回 400，用例不创建或不更新。
- Given 关联接口的请求模板已更新，When 再次执行用例，Then 使用接口的最新配置。
- Given 关联接口已删除，When 执行用例，Then 不发起请求，并返回明确的接口不存在错误。
### CASE-F02 管理标签和优先级
- 用户故事：作为维护者，我希望标记优先级和标签以便回归筛选。
- 规则：标签保存为数组；回归按包含标签筛选。
- 验收标准：保存和读取保持一致。

### CASE-F03 配置断言
- 用户故事：作为测试人员，我希望组合状态码和业务断言。
- 支持：json_eq、json_contains、json_gt、json_lt、response_time_lt、header_eq、header_contains、json_schema、db_eq。
- 规则：状态码和全部业务断言通过才算通过；异常转为断言失败。
- 验收标准：任一断言失败则总结果失败，服务不崩溃。

### CASE-F04 配置变量提取
- 用户故事：作为链路维护者，我希望从响应提取值供后续步骤使用。
- 规则：JSONPath 取第一个匹配值，写入共享上下文。
- 验收标准：提取值可用于后续请求和断言。

### CASE-F05 配置 setup/teardown SQL
- 用户故事：作为测试人员，我希望请求前准备、请求后清理数据。
- 规则：每次尝试前 setup；无论请求或断言异常，finally 执行 teardown。
- 验收标准：异常路径 teardown 仍执行，SQL 错误有失败证据。

### CASE-F06 配置数据集参数化
- 用户故事：作为测试人员，我希望用多行数据重复执行用例。
- 规则：逐行执行；数据集同名字段覆盖环境变量；全部行通过才总通过。
- 验收标准：任一行失败时总结果失败并保留每行结果。

### CASE-F07 配置失败重试
- 用户故事：作为测试人员，我希望自动重试瞬态失败。
- 规则：retries=R 时最多 R+1 次；任一次通过即停止。
- 验收标准：retries=2 最多 3 次；首次通过后不再请求。

### CASE-F08 单条用例执行
- 用户故事：作为成员，我希望立即执行一条用例。
- 流程：加载用例和接口 -> 环境上下文 -> 数据集/尝试 -> 断言和提取 -> 创建一条报告。
- 规则：缺失用例或接口不发请求，返回失败结果。
- 验收标准：结果含状态码、断言和尝试次数；结束必有报告。

### CASE-F09 多用例链路执行
- 用户故事：作为测试人员，我希望按顺序执行多个用例共享上下文。
- 规则：按 case_ids 顺序；步骤失败后继续；不使用 datasets、retries、SQL。
- 验收标准：前一步提取值可供后一步使用；缺失资源步骤失败并继续。

### CASE-F10 执行结果和步骤明细
- 用户故事：作为排障人员，我希望查看请求、响应、断言和错误。
- 规则：敏感字段遮罩；响应体最多 64 KiB，超出标记截断。
- 验收标准：详情可区分尝试/步骤，错误可定位。

## 7. 非功能要求
执行异常不得使进程崩溃；SQL 风险由使用者负责；证据可追溯且脱敏。

## 8. 当前实现与待确认项
已实现：单用例完整能力、链路共享上下文、报告落库。
当前限制：链路不执行 SQL/数据集/重试；变量无默认值。
待确认：失败即停止、更多断言类型和异步执行。
